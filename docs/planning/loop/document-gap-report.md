## 🔴 G-02 · 라운드 소요 시간이 문서 안에서 모순, 그 결과 **2차시 분할 근거가 흔들린다**

**근거**

| 위치 | 내용 |
|---|---|
| `03-user-flow.md:16-18` | 1라운드 13~25분, 2라운드 25~37분 → **라운드당 약 12분** |
| `03-user-flow.md:37` | "## 3. 한 라운드 안 (**약 4분**)" |
| `03-user-flow.md` §3 계산 | 이동 20초 + 문제 90초 + 베팅 60초 = **170초 ≈ 3분** |

같은 문서 안에서 12분과 4분이 충돌한다.

**더 중요한 함의**

2차시 분할은 기획 대화에서 이렇게 결정됐다 — *"6팀 순차 진행이면 라운드당 10분, 50분에 3라운드밖에 못 돈다."* 그런데 이후 **모둠 폰 동시 진행**으로 바꾸면서 라운드가 4분이 됐다. 그러면:

```
규칙 설명   8분
6라운드 × 4분 = 24분
정산        8분
─────────────────
합계       40분   → 1차시에 전부 끝난다
```

**2차시 분할을 만든 이유가 사라졌는데 결정은 그대로 남아 있다.** 그리고 2차시 분할 때문에 `M1`(판 코드 이어하기)·`P1-R2-T3`(사건 기록 복구)·`B5`(이어하기 검사)라는 **적지 않은 구현량**이 붙어 있다.

**영향받는 문서**: 01-prd §2·§4(M1), 02-trd §5, 03-user-flow §1·§2, 06-tasks P1-R2-T3·P6-T2, 08-test-plan B5

**필요한 것**: 사용자 결정. 아래 세 갈래 중 하나.
1. 2차시 유지 — 그러면 라운드당 12분이 되도록 **모둠 토론 시간을 별도 단계로 명시**해야 한다 (지금은 토론 시간이 어느 단계에도 없다)
2. 1차시 완결로 전환 — M1·복구 로직이 "있으면 좋은 것"으로 내려가고 구현량이 줄어든다
3. 1차시 목표 + 2차시 대비 — 기본은 1차시 완결, 못 끝내면 이어하기. 구현은 유지하되 시간표를 다시 씀

> 참고: 토론 시간을 명시하는 게 기획 목적("조용하던 애들이 말한다")에는 오히려 맞다. 지금 흐름에는 힌트를 받고 **이야기할 시간이 따로 잡혀 있지 않다** — 베팅 60초 안에 토론까지 하라는 셈이다.

## 🟠 G-01 · 문제를 어떻게 고르는지 정한 태스크가 없다

**근거**

| 위치 | 내용 |
|---|---|
| `04-database.md:148` | 상태에 `usedQuestions: {쉬움:[3,7], 중간:[1,5], 어려움:[2,9]}` 필드가 있다 |
| `teacher-setup.yaml:85` | 경고 문구가 "모자라면 **앞 라운드 문제를 다시 냅니다**"라고 약속한다 |
| `03-user-flow.md:150` | 같은 약속 |
| `06-tasks.md` | **이 동작을 구현하는 태스크가 없다** |

라운드 N에서 난이도 X를 고른 모둠에게 **어느 문항**을 줄지 정한 곳이 없다. `usedQuestions`를 읽고 쓰는 주체도 없다.

**필요한 것**: `P2-R4-T4 · 문제 선택기` 태스크 추가. 규칙은 다음을 정해야 한다 —
- 라운드×난이도 조합마다 문항 1개 배정 (같은 난이도를 고른 모둠은 같은 문제 — 선생님 결정)
- 이미 낸 문항은 `usedQuestions`에 기록
- 남은 문항이 없으면 가장 오래된 것부터 재사용
- 문항 배정은 판 생성 시 미리 다 정한다 (라운드마다 뽑으면 캐시 복구 시 달라진다)

## 🟠 G-03 · 난이도별 힌트 풀 크기가 요구와 충돌

**근거**

| 위치 | 내용 |
|---|---|
| `04-database.md:149` | `hintPlan: {어려움:[0,3,5], 중간:[1,2,6], 쉬움:[4,7,8]}` — 난이도별 **3개** |
| `06-tasks.md P2-R3-T3` | acceptance: "한 모둠이 6라운드 힌트 지급 시 **같은 문장이 두 번 안 나옴**" |
| `06-tasks.md P2-R3-T4` | G3-b: "**어려움만 6번** 고른 모둠이 1·2·3등을 좁힐 수 있음" |

어려움을 6번 고른 모둠은 서로 다른 어려움 힌트 6개가 필요한데 풀에는 3개뿐이다. **acceptance 두 개가 동시에 만족될 수 없다.**

**필요한 것**: `02-trd §6-2`와 `04-database §6`에 **난이도별 힌트 풀 최소 6개** 명시. 그리고 힌트문구 탭의 종류가 난이도별로 3종뿐이므로(어려움: 순위확정/상위확정/부정확정), 같은 종류를 **다른 동물에 적용해** 6개를 만들어야 한다. 예: "B는 최종 1등입니다" / "F는 최종 5등입니다" — 같은 틀, 다른 대상.

## 🟡 G-05 · QR 코드가 "외부 라이브러리 금지"와 충돌 (미결)

**근거**: `06-tasks.md P4-S1-T2`가 "QR(외부 라이브러리 없이 직접 생성)"이라고 적고, 비고에 "순수 JS 구현 또는 주소만 크게 (판단 필요)"로 미결 표시.

QR 인코더를 직접 짜는 건 만만치 않다(리드-솔로몬 오류정정 포함). `07-coding-convention §10`은 CDN을 금지한다.

**필요한 것**: 결정. 실용적으로는 **주소만 크게 표시 + 짧은 단축 경로**로 충분하다 — 학생은 어차피 판 코드 4자리를 손으로 입력해야 하므로 QR이 절약하는 건 주소 입력 한 번뿐이다.
